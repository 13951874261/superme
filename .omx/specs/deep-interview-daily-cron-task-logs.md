# 执行规格：在后台任务中心查看每日定时任务详细日志

## 1. 元数据

- 来源：Deep Interview
- Profile：Standard
- Context：Brownfield
- 最终歧义度：3%
- 阈值：20%
- Context snapshot：`.omx/context/daily-cron-task-logs-20260808T105600Z.md`
- Interview：`.omx/interviews/daily-cron-task-logs-20260808T105600Z.md`
- 状态：需求已确认，可进入架构/测试计划

## 2. 意图

让用户无需登录服务器或查看 `journalctl`，即可从现有顶栏任务入口确认每日 02:00 后台生成是否执行、执行到哪一步、每一步使用了什么入参及入参如何获取，并能人工重跑失败项或整次任务。

## 3. 期望结果

1. 顶栏“提纯：查看队列”改为“后台任务：查看队列”。
2. 抽屉“提纯任务中心”改为“后台任务中心”。
3. 现有材料、视频、博弈、听力等任务行为保持不变。
4. 最近 7 天的每日定时执行以任务卡形式出现在任务中心。
5. 每次执行只有一张主卡，内部按以下模块展示：
   - 每日唤醒
   - 每日破绽词汇
   - 每日长文
   - 每日精听
6. 用户可查看模块状态、进度、执行时间、错误、实际入参和入参获取方法。
7. 用户可整次重新执行，或仅重跑失败模块/失败长文组合。
8. 前端仅能查看和重跑当前登录用户的数据，不显示同一 Cron 中其他用户的信息。

## 4. 范围

### 4.1 在范围内

- Cron 执行记录持久化，保留最近 7 个上海日历日。
- 自动 02:00 执行、现有手动 Cron 入口及任务中心发起的重跑均创建独立运行记录。
- 一次运行记录包含父级状态和4个模块的结构化状态。
- 长文记录包含 64 个组合的独立结果，但默认只展示汇总与失败项。
- 保存本次 Dify 业务入参快照，不保存密钥或 Authorization Header。
- 保存每个入参的来源、查询方式、转换方式和兜底方式。
- 重跑失败项时复用原始业务入参快照。
- 整次重新执行时重新获取当前业务入参。
- “整次重新执行”只执行当前登录用户的四个模块，不启动全局多用户 Cron。
- 新执行记录不得覆盖原执行记录。
- 运行中任务在前端按现有轮询方式更新。
- 任务中心文案泛化。
- 可加入轻量的卡片展开、日志展开动画。

### 4.2 明确不在范围内

- 不改变现有每日 02:00 触发时间和时区策略。
- 不新增无人值守自动重试策略。
- 不提供日志下载、导出或外部日志平台接入。
- 不展示或存储 Dify API Key、Bearer Token、环境变量密钥值。
- 不把64个长文组合平铺成64张顶层任务卡。
- 不重构与本功能无关的现有异步任务。
- 不修改每日内容生成规则、Prompt 或 Dify 工作流业务逻辑。

## 5. 术语

- “每日运行”：一次自动或人工触发的完整每日后台任务。
- “模块”：唤醒、破绽词、长文、精听四个父级步骤。
- “组合”：长文中的 `genre × cefr_level × duration` 单元。
- “入参快照”：某次运行实际传给生成逻辑的业务参数，不含任何认证信息。
- “入参来源”：参数读取位置、查询条件、转换和兜底说明。
- “整次重新执行”：读取当前数据后创建新的完整运行。
- “重跑失败项”：读取原运行快照后，仅创建并执行原失败范围的新运行。

## 6. 数据与持久化要求

### 6.1 推荐模型

新增独立 SQLite 持久化，不延长现有 `taskQueue` 的全局 TTL，避免改变其他任务行为。

建议使用：

- `daily_cron_runs`
  - 运行 ID、业务日期、触发来源、父运行 ID
  - `pending/running/completed/partial_failed/failed`
  - 总进度、开始/结束时间、汇总、错误
- `daily_cron_steps`
  - 所属运行、模块、组合键、用户
  - 状态、进度、开始/结束时间、错误
  - `inputs_json`
  - `input_sources_json`
  - 结果摘要
- `daily_cron_log_events`
  - 所属运行/步骤、级别、时间、消息和结构化上下文

允许实施阶段在不改变以上能力的前提下合并表或将低价值日志事件存入步骤 JSON。

### 6.2 保留策略

- 按 `Asia/Shanghai` 日期保留最近7天。
- 清理只删除超过保留期的 Cron 日志记录，不删除业务内容表。
- 正在运行的记录不得被清理。
- 服务重启后，遗留 `running` 记录应转为 `failed/interrupted`，并保留可见错误。

## 7. 入参日志契约

每个参数至少记录：

- `name`：参数名。
- `value`：本次实际值。
- `valuePreview`：默认展示的安全摘要。
- `sourceType`：数据库、运行时、配置、组合循环或原运行快照。
- `sourceRef`：表/字段、函数或组合维度。
- `queryRule`：必要的筛选条件描述。
- `transform`：截断、拼接、排序、去重、默认值等。
- `fallback`：无数据时采用的值或行为。
- `sensitive`：是否默认折叠。
- `friendlyDescription`：面向用户的中文获取方式说明。
- `technicalDetails`：表名、字段名、函数、筛选、排序、转换和兜底规则。

### 7.1 唤醒/破绽词至少记录

- `theme`
- `history_exclude`
- `user_current_profile`
- `_system_time`
- `_system_timestamp_ms`
- Dify 外层 `user`
- `response_mode`

破绽词还需记录：

- 随机 Focus。
- 日期与 Salt。
- 最终 `dynamicTheme`。
- `history_exclude` 的实际选择规则。

### 7.2 长文至少记录

- `theme`
- `cefr_level`
- `genre`
- `duration`
- `history_exclude`
- `user_flaws`
- `user_current_profile`
- `_system_time`
- `_system_timestamp_ms`
- `query`
- `response_mode`
- Dify 外层 `user`

### 7.3 安全规则

- API 不得返回任何 API Key 或 Authorization Header。
- 不得把服务端环境变量对象写入日志。
- 画像、薄弱点、历史词汇等长文本默认折叠。
- 前端展开敏感长文本必须是用户主动操作。
- 错误栈返回前应移除可能包含的认证 Header 和 URL 查询密钥。
- 服务端必须按当前登录用户过滤运行、步骤、日志和入参；不得依赖前端隐藏实现隔离。

## 8. 执行采集要求

### 8.1 自动执行

`scheduleDailyPackCron` 命中 02:00 后：

1. 创建每日运行记录。
2. 记录触发时间、业务日期、目标用户数量与选人策略。
3. 启动模块步骤并持续更新状态。
4. 每个长文组合单独记录开始、结束、重试次数和错误。
5. DailyListen 作为同一次运行的第四模块记录。
6. 所有模块结束后生成父级汇总。

### 8.2 状态聚合

- 全部成功：`completed`。
- 有成功也有失败：`partial_failed`。
- 所有核心模块失败或运行无法启动：`failed`。
- 仍在执行：`running`。
- 进度以已结束执行单元数计算，不根据日志条数计算。

### 8.3 Console 保留

现有关键 `console.log/warn/error` 可以保留；结构化日志记录作为 UI 数据源，不能依赖抓取 stdout。

## 9. API 契约

建议新增独立 Cron API，现有 `/api/tasks` 合同保持兼容：

- `GET /api/daily-cron/runs?days=7`
  - 返回最近7天与当前登录用户相关的运行摘要。
- `GET /api/daily-cron/runs/:runId`
  - 仅在运行属于当前登录用户时返回模块、组合、日志和安全入参。
- `POST /api/daily-cron/runs/:runId/rerun`
  - `mode=all_current`：整次重新执行，重新获取当前入参。
  - `mode=failed_snapshot`：仅重跑失败范围，复用原快照。
  - 可选 `stepId/comboKey` 限定失败范围。

要求：

- 同一重跑按钮连续点击必须防重复提交。
- API 返回新运行 ID，原记录只增加关联信息，不被覆盖。
- 非失败步骤不得通过 `failed_snapshot` 模式重跑。
- 最近7天查询不得返回密钥。
- `all_current` 只重跑当前登录用户，不调用全局多用户 Cron 入口。
- 当前用户无权读取或重跑其他用户的运行记录。

## 10. 前端交互

### 10.1 顶栏

- 标签由“提纯”改为“后台任务”。
- 有运行中任务时继续显示运行数量。
- Cron 运行应计入运行数量。

### 10.2 后台任务中心

- 标题：“后台任务中心”。
- 副标题覆盖网页提取、视频、每日生成等后台任务。
- 现有任务与每日运行按创建时间统一排序。
- 每日运行卡显示：
  - 日期与触发来源。
  - 父级状态和总进度。
  - 4个模块的成功/失败/运行中数量。
  - “查看详情”。
  - 根据状态显示“整次重新执行”或“重跑失败项”。

### 10.3 每日运行详情

- 四个模块折叠分区。
- 长文默认显示完成数、失败数和总数。
- 失败组合默认展开错误摘要。
- 成功组合可按需展开。
- 入参区分成“实际值”和“获取方式”。
- 获取方式默认显示中文业务说明，并提供“技术详情”展开区显示表/字段/函数/筛选和转换规则。
- 敏感长文本默认折叠。
- 重跑前弹出确认，明确说明使用“当前入参”还是“原始快照”。

## 11. 动画要求

项目是 React，不使用面向 Vue/Svelte 的 GSAP 生命周期模式。

若实施轻量动画：

- 使用现有 `gsap` 与 `@gsap/react`，不新增依赖。
- 使用 `useGSAP()` 和组件根 `ref` 作为 scope。
- 事件回调产生的动画使用 `contextSafe`。
- 动画只使用 `x/y/autoAlpha/scale` 等 transform/opacity 属性。
- 遵循 `prefers-reduced-motion`；用户选择减少动态效果时跳过或将 duration 设为0。
- 不替换现有业务状态逻辑，也不因动画延迟日志渲染。

## 12. 决策边界

实施者可自行决定：

- SQLite 表的最终拆分方式。
- API 内部 service/repository 拆分。
- React 子组件拆分。
- 图标、间距和轻量动画参数。
- 轮询复用或单独 Cron 轮询的内部实现。

实施者必须再次询问：

- 需要改变7天保留期。
- 需要改变02:00触发策略。
- 需要新增自动重试。
- 需要展示更多敏感信息。
- 需要改变现有任务的数据合同或清理策略。
- 需要增加跨用户或管理员日志可见能力。

## 13. 可测试验收标准

1. 自动 Cron 启动后，任务中心出现一张新的每日运行卡，状态从运行中更新到终态。
2. 一张卡内能看到唤醒、破绽词、长文、精听四个模块。
3. 长文显示总组合数、成功数、失败数；不会生成64张顶层卡。
4. 任一失败组合能查看错误、实际入参和每个入参的获取方法。
5. 唤醒/破绽词/长文的 Dify Key 和 Authorization Header 在数据库、API 响应和 UI 中均不存在。
6. 用户画像、薄弱点和历史词汇默认折叠，主动展开后可见本次快照。
7. 任务中心能查看最近7天记录；超过7天记录被清理。
8. 服务重启后历史记录仍存在，遗留运行中记录标记为中断失败。
9. 点击“重跑失败项”创建新记录并使用原始入参快照，仅执行原失败范围。
10. 点击“整次重新执行”创建新记录并重新获取当前入参。
11. 重跑不覆盖原记录，且连续点击不会创建重复运行。
12. 现有材料、视频、博弈和听力任务仍能正常展示、轮询和执行原完成操作。
13. 顶栏和抽屉文案更新为通用后台任务语义。
14. 若启用 GSAP，组件卸载后无残留 tween，减少动态效果设置得到尊重。
15. 当前用户只能查询和重跑自己的日志；使用其他用户运行 ID 请求时必须拒绝或返回不存在。
16. 入参来源默认显示中文说明，展开技术详情后可看到准确的表/字段/函数/筛选与转换规则。
17. “整次重新执行”只处理当前用户，不触发其他目标用户。

## 14. 测试场景

### 场景 A：全成功自动运行

- 菜单路径：顶栏“后台任务：查看队列”。
- 测试数据：一个近7天登录且有主题的用户；四模块均成功。
- 预期：出现一张 completed 卡；模块和组合统计正确；入参来源可查。

### 场景 B：部分长文失败

- 测试数据：模拟一个指定组合 Dify 失败。
- 预期：父运行 `partial_failed`；失败组合默认可见；其他成功组合不受影响。

### 场景 C：失败项重跑

- 操作：在场景 B 记录点击“重跑失败项”。
- 预期：创建新运行；复用旧参数快照；只执行失败组合；旧记录保持不变。

### 场景 D：整次重新执行

- 测试数据：先修改主题或用户画像。
- 操作：历史记录点击“整次重新执行”。
- 预期：新运行记录显示新的当前入参及获取日志。

### 场景 E：安全

- 测试数据：服务端配置有效 Dify Key。
- 预期：数据库、API 和 UI 搜索不到 Key、Bearer Header；长文本默认折叠。

### 场景 F：保留与重启

- 测试数据：构造8天记录和一个 running 记录后重启。
- 预期：第8天记录被清理；running 记录变为中断失败；最近7天仍可查看。

### 场景 G：回归

- 菜单路径：材料提纯、视频转写、博弈历史、听力补跑。
- 预期：原任务创建、轮询、日志、结果操作与修改前一致。

### 场景 H：用户隔离

- 测试数据：用户 A、用户 B 各有一条 Cron 运行。
- 操作：用户 A 查询用户 B 的运行 ID，并尝试重跑。
- 预期：详情不可见、重跑被拒绝；任务中心只显示用户 A。

### 场景 I：入参来源双层展示

- 操作：展开某个 Dify 入参。
- 预期：默认看到中文获取说明；继续展开技术详情后看到表/字段/函数、筛选、排序、转换和兜底规则。

## 16. 剩余风险

- 当前 Cron 将 DailyPack ready 作为 `continue` 条件，可能同时跳过该用户的长文；日志功能会暴露但不会自动修复此既有行为。
- 长文主路径提交异步任务后即返回，采集“真正完成”状态需要接入其异步完成回调，而不能只记录 HTTP 已受理。
- 现有 Cron 防重复标记只在内存，多实例仍可能重复触发；本规格不改变调度策略，但运行记录应能展示重复执行事实。
- `server.js` 部分中文日志存在乱码；结构化新日志必须使用明确的 UTF-8 文案，不复制乱码字符串。
